# طرح بازیابی بکاپ از پنل ادمین

وضعیت: طرح در ۲۰۲۶-۱۰-۱۸ توسط کاربر تأیید شد؛ اجرای مستقیم در همین گفتگو درخواست شد.

## هدف و محدوده

ادمین اصلی روی نصب تازهٔ سرور مقصد، ZIP موجود داشبورد را آپلود می‌کند؛ فایل
پیش از اجرا بررسی می‌شود، خلاصهٔ داده نمایش داده می‌شود و پس از تأیید نهایی،
تمام دیتابیس و کلید اصلی با هم برمی‌گردند. کاربران و نماینده‌های واقعی مبدأ،
پنل‌های VPN، listenerها، Docker network، firewall و سرویس‌های دیگر تغییر نمی‌کنند.

بازیابی از UI فقط روی نصب تازه مجاز است: هیچ نماینده، کاربر، اتصال PanelConfig
یا عملیات حسابداری وجود نداشته باشد. وجود ادمین اولیه و گزارش ورود مجاز است.
این شرط در backend هنگام آپلود، تأیید و پیش از نصب مجدداً بررسی می‌شود؛ مخفی‌کردن
دکمه کافی نیست. جایگزینی پنل فعال و ادغام دو دیتابیس در این تغییر پیاده نمی‌شود.

## مسیر کاربر

۱. در تب بکاپ ادمین، دکمهٔ «بازیابی بکاپ» نمایش داده می‌شود. روی نصب دارای داده،
دلیل غیرفعال‌بودن و لینک راهنمای انتقال دیده می‌شود.

۲. ادمین ZIP را انتخاب می‌کند. حداکثر حجم فایل آپلودی ۶۴ MiB و حداکثر محتوای
بازشده ۵۱۲ MiB است. محدودیت جریان ورودی نیز روی سرور اعمال می‌شود و Content-Length
یا پسوند فایل به‌تنهایی ملاک نیست. فایل با نام تصادفی و دسترسی خصوصی نگه داشته می‌شود.

۳. پیش‌نمایش، تاریخ بکاپ، SHA-256، تعداد کاربران، نماینده‌ها، اتصال‌ها و تنظیمات
peer و وجود اطلاعات بازیابی را نشان می‌دهد؛ هیچ token، رمز، UUID یا کلیدی در
پاسخ یا log چاپ نمی‌شود. checksum صحت انتقال/ساختار را بررسی می‌کند، نه اصالت
رمزنگاری‌شدهٔ سازنده؛ فقط فایل مورد اعتماد اپراتور پذیرفته شود.

۴. ادمین هشدار جایگزینی ادمین موقت و نیاز به ورود با حساب‌های داخل بکاپ را می‌بیند.
رمز فعلی ادمین مقصد و در صورت فعال‌بودن 2FA، کد فعلی برای تأیید دوباره لازم است.
توکن پیش‌نمایش کوتاه‌عمر، یک‌بارمصرف، مقید به ادمین و hash همان فایل است. کنترل
same-origin و نرخ تلاش، از ارسال بین‌سایتی و آزمون رمز جلوگیری می‌کند.

۵. پس از تأیید، درخواست‌های تغییر داده موقتاً متوقف، snapshot برگشت از نصب
تازه تهیه و درخواست بازیابی ماندگار ثبت می‌شود. فقط فرآیند همین داشبورد با
restart policy موجود کانتینر دوباره اجرا می‌شود؛ Docker socket داخل کانتینر
قرار نمی‌گیرد. UI انتظار کوتاه و سپس ورود دوباره را نشان می‌دهد.

۶. اگر بکاپ peer دارای مسیر خصوصی مبدأ باشد، هشدار بررسی مسیر مقصد نشان داده
می‌شود. بازیابی خودکار، آدرس یا gateway یا CA را حدس نمی‌زند. پیش از بازکردن
مسیر عمومی و ربات/پل، اتصال‌های بازیابی‌شده باید طبق راهنمای انتقال بررسی شوند.

## اعتبارسنجی پیش از قبول

- احراز ادمین واقعی در DB جاری، محدودیت اندازه/تعداد فایل و فضای کافی.
- فرمت pvnet-backup-v1 و complete=true؛ مسیرهای مجاز، عدم symlink، عدم تکرار
  entry و checksum و اندازهٔ واقعی تمام payloadها.
- استخراج به staging خصوصی و خالی با ابزار فعلی؛ integrity_check و
  foreign_key_check موفق. وجود حداقل یک ادمین و ساختار جدول/ستون سازگار با
  schema نسخهٔ درحال اجرا؛ بکاپ ناسازگار یا خراب بدون تغییر DB جاری رد می‌شود.
- وجود APP_SECRET معتبر؛ بازکردن واقعی مقادیر رمزگذاری‌شدهٔ PanelConfig،
  تنظیمات peer و TOTP با همان کلید؛ فرمت peer و ارتباط آن با PanelConfig بررسی
  شود. تست ارتباط خارجی هنگام اعتبارسنجی انجام نمی‌شود تا دادهٔ آپلودشده درخواست
  شبکهٔ ناخواسته نسازد.
- ژورنال‌ها، رزروها، وضعیت عمداً غیرفعال و داده‌های حسابداری عیناً حفظ شوند؛
  restore هیچ create/update/delete/reset خودکار به پنل خارجی نمی‌فرستد.
- در صورت وجود فایل‌های native panel در آرشیو قدیمی، اعتبارشان بررسی ولی روی
  پنل‌های خارجی نصب نمی‌شوند؛ UI روشن می‌گوید فقط داشبورد بازیابی می‌شود.

## اعمال آفلاین و بازیابی پس از قطع برق

DB باز زیر Prisma جایگزین نمی‌شود. entrypoint پیش از اجرای Node درخواست
بازیابی ماندگار را می‌خواند، شرط نصب تازه و hash فایل را دوباره بررسی و staging
را آماده می‌کند. روند نصب مراحل ماندگار دارد تا قطع برق میان تعویض DB و کلید،
برنامه را با ترکیب اشتباه بالا نیاورد. پیش از تکمیل هر دو، Node اجرا نمی‌شود.

کلید بازیابی در فایل خصوصی data volume ذخیره و entrypoint آن را به APP_SECRET
فرآیند Node می‌دهد؛ env سرور میزبان یا فایل سایر سرویس‌ها بازنویسی نمی‌شود.
اسکریپت‌های مدیریتی داخل کانتینر نیز باید همان کلید مؤثر را بخوانند؛ تغییر
کلید نباید configure-node-sync یا بکاپ روزانه را با کلید قدیمی اجرا کند.

WAL/SHM قدیمی فقط متعلق به DB مقصدِ متوقف و حفاظت‌شده است و با DB تازه مخلوط
نمی‌شود. پایان موفق و نتیجهٔ بازیابی خصوصی ثبت می‌شود؛ توکن‌های آپلود دیگر
نامعتبر می‌شوند. فایل‌های staging منقضی پاک می‌شوند و snapshot برگشت جداگانه
با دامنهٔ حذف مشخص نگهداری می‌شود. شکست پیش از نصب، DB قبلی را دست‌نخورده
می‌گذارد؛ شکست حین نصب تا رفع یا برگشت هماهنگ DB/کلید، برنامه را بالا نمی‌آورد.

## بخش‌های درگیر

- src/components/panel/backups-tab.tsx: انتخاب فایل، پیش‌نمایش، تأیید و وضعیت انتظار.
- مسیر اختصاصی src/app/api/admin/backups/restore: پیش‌نمایش و تأیید مجاز.
- ابزار server-side محدود آپلود و state بازیابی در data volume.
- scripts/panel-backup.py و ابزار startup جدا: اعتبارسنجی، snapshot، نصب آفلاین.
- docker/entrypoint.sh و docker/Dockerfile: اجرای مرحلهٔ پیش از Node و بسته‌بندی.
- اسکریپت‌های خوانندهٔ APP_SECRET و gate درخواست‌های تغییر داده هنگام انتظار.
- راهنمای انتقال، README و حافظهٔ عملیاتی.

## آزمون و استقرار

ابتدا آزمون‌های ناموفق برای آرشیو خراب/ناقص، traversal/zip bomb، کلید اشتباه،
schema ناسازگار، مقصد دارای داده، آپلود هم‌زمان، توکن منقضی/مصرف‌شده و قطع برق
میان مراحل نوشته می‌شود. تست موفق با کلید مبدأ متفاوت از مقصد باید تمام
جدول‌ها، رمزگشایی، ورود ادمین/نماینده و تنظیمات peer را پس از restart تأیید کند.

آزمون API ناشناس/نماینده، same-origin، تأیید رمز/2FA، UI دسکتاپ/موبایل و پاک‌سازی
staging لازم است. پذیرش container با کپی داده و پنل‌های شبیه‌سازی‌شده، بدون
پورت عمومی یا mount دادهٔ واقعی انجام شود؛ تعداد درخواست نوشتن به پنل‌های خارجی
در طول restore باید صفر باشد.

روی production فقط قابلیت نصب می‌شود؛ بکاپی روی دادهٔ واقعی restore نمی‌شود.
پیش از استقرار snapshot و image برگشت حفظ می‌شوند؛ همان loopback bind، network،
env و volume باقی می‌مانند و هویت/پورت سرویس‌های دیگر پیش و پس مقایسه می‌شوند.
تایمر و اعتبار کلید مؤثر بعد از استقرار جدا بررسی می‌شوند.
