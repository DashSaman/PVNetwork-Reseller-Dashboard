# بازیابی بکاپ داشبورد روی سرور جدید

این راهنما برای بکاپ `pvnet-backup-v1` و نسخهٔ دارای اصلاح همگام‌سازی نود
(`5025d9f` یا نسخهٔ سازگار بعدی) است. دستورها برای اپراتور root روی Linux هستند؛
این سند به معنی انجام انتقال روی سرور فعلی نیست.

## چه چیزهایی برمی‌گردند؟

کل SQLite داشبورد: ادمین و ورود دومرحله‌ای، نماینده‌ها و رمزهای هش‌شده، کاربران
و مالکیت و subId، تخصیص‌ها و موجودی و مصرف قطعی، اینباندهای مجاز، دسترسی‌ها،
برند و دامنه، اتصال‌های پنل‌ها و رمزهای ذخیره‌شده، تنظیمات رمزگذاری‌شدهٔ
`nodeSyncPeers:*`، ژورنال عملیات و گزارش‌ها. `APP_SECRET` داخل بکاپ برای بازکردن
اطلاعات رمزگذاری‌شده ضروری است؛ با کلید جدید جایگزین نشود.

دیتابیس و تنظیمات خود 3x-ui/Xray، کاربران زنده و شمارنده‌های پنل‌های خارجی،
image Docker، فایل‌های میزبان `.env` و `.installer-env`، شبکهٔ Docker، vhost/TLS/DNS،
فایل‌های دلخواه میزبان و تایمر systemd داخل این بکاپ نیستند. دادهٔ زندهٔ مصرف،
انقضا و وضعیت از همان پنل‌های موجود خوانده می‌شود. برای انتقال خود VPNها، این
ZIP کافی نیست؛ به پنل پیکنیکی یا دیتابیس آن برای این انتقال دست نزنید.

## ۱. آماده‌سازی بدون تداخل

### مسیر ساده از پنل ادمین

روی مقصد، نسخهٔ Docker جدید این ریپو را نصب و با ادمین اولیه وارد شوید؛ هنوز
نماینده، کاربر، اتصال پنل یا تنظیمات نسازید. در «بکاپ ← بازیابی بکاپ»، ZIP مورد
اعتماد را انتخاب و «بارگذاری و بررسی بکاپ» را بزنید. شمار کاربران/نماینده‌ها،
تاریخ و SHA-256 را بازبینی و با رمز فعلی ادمین مقصد و کد 2FA در صورت فعال‌بودن
تأیید کنید. پیش‌نمایش ۱۵ دقیقه اعتبار دارد؛ آپلود جدید پیش‌نمایش قبلی را لغو می‌کند.

حداکثر ZIP ۶۴ MiB و محتوای بازشده ۵۱۲ MiB است؛ حداقل ۱٫۲ GiB فضای آزاد لازم
است. نسخهٔ ناسازگار یا فایل ناقص پیش از تغییر DB رد می‌شود. نصب دارای داده
اجازهٔ بازیابی نمی‌دهد. فقط کانتینر داشبورد طبق restart policy موجود دوباره
اجرا می‌شود؛ سپس با ادمین داخل بکاپ وارد شوید. پنل‌ها و سرویس‌های دیگر دست‌نخورده‌اند.

کلید مؤثر در فایل خصوصی `data/.app-secret` باقی می‌ماند؛ env اصلی میزبان خودکار
بازنویسی نمی‌شود. این فایل را در انتقال دستی بعدی همراه DB حفظ کنید یا از ZIP
جدید استفاده کنید؛ app، بکاپ روزانه، CLI بکاپ و configure-node-sync آن را می‌خوانند.
به image قدیمی فاقد این پشتیبانی برنگردید. برگشت هماهنگ DB/کلید لازم است.
snapshot نصب تازه پیش از اعمال در `data/.restore/rollback` نگهداری می‌شود؛ این
مسیر مشمول حذف روزانهٔ ZIPهای تب بکاپ نیست. فایل‌های موقت آپلود در آپلود بعدی یا
شروع مجدد پاک می‌شوند؛ عملیات ناتمام از pending در شروع بعدی ادامه پیدا می‌کند
و تا تکمیل DB و کلید، برنامه بالا نمی‌آید. این فایل‌ها نیز خصوصی‌اند.

پس از ورود، بررسی مسیر نود، TLS، مصرف زنده و مراحل پذیرش بخش ۵ همچنان لازم است.
این دکمه شبکه، دامنه، وب‌سرور و سرورهای VPN را منتقل نمی‌کند. برای نصب غیر Docker
یا کار اپراتوری از مسیر دستی زیر استفاده کنید.

- ZIP را از تب بکاپ ادمین دانلود و خارج از سرور، خصوصی نگه دارید؛ نگهداری مدیریت‌شده
  روی مبدأ فقط پنج روز است. فایل حاوی کلید و اطلاعات اتصال است و نباید وارد Git شود.
- برای زمان جابه‌جایی واقعی، تغییرات داشبورد مبدأ و ربات/پل را موقتاً متوقف کنید،
  سپس بکاپ تازه بگیرید. این توقف، سرویس VPN کاربران را متوقف نمی‌کند. بکاپ قدیمی
  تغییرات پس از زمان خودش را ندارد؛ فقط یک داشبورد اجازهٔ نوشتن داشته باشد.
- روی مقصد، سیستم‌عامل و فضای دیسک، Docker موجود، نام کانتینر و network و مسیرهای
  نصب، TCP/UDPهای درحال استفاده، وب‌سرور و vhostهای موجود را ثبت کنید. دستورهای
  خواندنی: `df -h`، `ss -lntup`، `docker ps -a` و `docker network ls`.
- مسیر نمونه `/opt/pv-reseller`، نام `pv-reseller-dashboard` و شبکهٔ `pv_reseller_net`
  باید آزاد یا متعلق به همین استقرار باشند. نام یک سرویس ناشناس را تصاحب نکنید.
  subnet شبکهٔ جدید نباید با شبکه‌های میزبان، Docker یا VPN هم‌پوشانی داشته باشد.
- پورت نمونه `127.0.0.1:31080` باید آزاد باشد؛ اگر اشغال است، پورت آزاد دیگری را
  فقط برای این داشبورد انتخاب و upstream همین vhost را اصلاح کنید. برنامه را روی
  `0.0.0.0:31080` منتشر نکنید. پورت‌های 80/443 متعلق به وب‌سرور موجود می‌مانند.
- روی میزبان اشتراکی، نصب‌کنندهٔ کامل را کورکورانه اجرا نکنید: بسته‌ها و vhost
  می‌سازد و Apache را reload می‌کند. بخش Docker زیر را با وابستگی‌های آماده اجرا
  کنید؛ reverse proxy موجود را فقط برای دامنهٔ داشبورد پیکربندی کنید. Docker،
  شبکه‌ها، firewall و سرویس‌های دیگر را restart، پاک‌سازی یا بازنویسی نکنید.

## ۲. اعتبارسنجی و استخراج در مقصد خالی

مسیرها و مقدار `ARCHIVE` نمونه‌اند و باید با مسیر امن واقعی جایگزین شوند.
سورس را از ریپو با نسخهٔ سازگار آماده کنید؛ `docker/Dockerfile` فایل build است.
مثلاً پس از احراز آزادبودن مسیر مقصد، سورس را در `/opt/pv-reseller/app` clone
کنید و revision انتخاب‌شده را ثبت کنید. روی clone موجود، ابتدا تغییرات محلی را
بررسی کنید؛ reset اجباری انجام ندهید. بلوک‌ها در یک نشست Bash اجرا می‌شوند و
در خطا باید متوقف شوند؛ قبل از نوشتن هر بلوک، مقادیر مسیرها را بازبینی کنید.

```bash
set -euo pipefail
umask 077
ARCHIVE=/root/pvnet-migration/pvnet-backup.zip
RESTORE=/root/pvnet-migration/restored
REPO=/opt/pv-reseller/app
sha256sum "$ARCHIVE"
python3 "$REPO/scripts/panel-backup.py" verify "$ARCHIVE"
python3 "$REPO/scripts/panel-backup.py" restore "$ARCHIVE" "$RESTORE"
```

SHA-256 را با مقدار ثبت‌شده هنگام دریافت تطبیق دهید. `verify` باید `valid:true`
و `complete:true` بدهد؛ برای بکاپ فعلی داشبورد، `panelCount:0` طبیعی است.
اسکریپت مسیرهای ZIP، اندازه و checksum فایل‌ها را بررسی می‌کند؛ `restore` نیز
integrity SQLite را کنترل می‌کند و مقصد غیرخالی یا symlink را رد می‌کند.
خروجی: `data/custom.db`، `recovery.env`، `manifest.json` و پوشهٔ خالی `panels/`.
وجود manifest موفق به‌تنهایی تأیید اتصال به پنل خارجی نیست.

## ۳. داده و کلید، پیش از اولین اجرای برنامه

این نمونه فقط برای **مقصد تازه و خالی** است. اگر همین داشبورد قبلاً روی مقصد
اجرا شده، ابتدا فقط کانتینر و تایمر متعلق به آن را متوقف و از DB، فایل‌های WAL/SHM
و env آن نسخهٔ خصوصی بگیرید؛ ادامهٔ این نمونه روی مسیر غیرخالی مجاز نیست.
فایل DB را روی دیتابیس باز یا کنار WAL قدیمی جایگزین نکنید.

```bash
INSTALL=/opt/pv-reseller
test ! -e "$INSTALL/data/custom.db"
test ! -e "$INSTALL/.env"
test ! -e "$INSTALL/data/custom.db-wal"
test ! -e "$INSTALL/data/custom.db-shm"
install -d -m 700 "$INSTALL/data"
install -m 600 "$RESTORE/data/custom.db" "$INSTALL/data/custom.db"
install -m 600 "$RESTORE/recovery.env" "$INSTALL/.env"
```

همهٔ preconditionها باید موفق باشند. `.env` بالا کلید اصلی را دارد؛ محتوایش را
چاپ یا در history وارد نکنید. سایر envهای ضروری استقرار قبلی را جداگانه و امن
بازسازی کنید؛ ZIP کپی کامل env نیست. `DATABASE_URL` باید فقط DB بازیابی‌شده باشد.
مالکیت volume باید با کاربر image سازگار باشد (image فعلی با root اجرا می‌شود؛
برای image با UID متفاوت، فقط همین data directory را متناسب کنید).

ادمین و رمز فعلی از DB برمی‌گردند و لازم نیست دوباره ساخته شوند. `ADMIN_PASSWORD`
رمز ادمین موجود را عوض نمی‌کند. نیاز به bootstrap ادمین تازه نشانهٔ DB خالی/اشتباه
است؛ قبل از ورود و ساخت ادمین جدید، mount و مسیر DB را بررسی کنید.

## ۴. شبکه، image و دسترسی امن به نود

از image سالم ذخیره‌شده با `docker save/load` (خارج از ZIP) یا build از نسخهٔ
سازگار سورس استفاده کنید. image قدیمیِ فاقد اصلاح node sync را راه‌اندازی نکنید.
برای build نمونه: `docker build -f "$REPO/docker/Dockerfile" -t pv-reseller-dashboard:migration "$REPO"`.

پس از بررسی عدم هم‌پوشانی subnet و آزادبودن نام شبکه، شبکهٔ اختصاصی بسازید یا
شبکهٔ متعلق به همین داشبورد را استفاده کنید. مقدار `NETWORK` زیر باید همان باشد.
برای شبکهٔ تازه، تنها پس از تأیید محدودهٔ آدرس‌های انتخابی می‌توان
`docker network create pv_reseller_net` را اجرا کرد؛ شبکهٔ موجود را حذف یا بازسازی نکنید.
کانتینر موجود با نام مشابه را خودکار stop/rm نکنید. اجرای نمونه، پس از همهٔ بررسی‌ها:

```bash
IMAGE=pv-reseller-dashboard:migration
NETWORK=pv_reseller_net
APP_PORT=31080
docker run -d --name pv-reseller-dashboard --restart unless-stopped \
  --network "$NETWORK" --env-file "$INSTALL/.env" \
  -e NODE_ENV=production -e PORT=3000 -e HOSTNAME=0.0.0.0 \
  -e DATABASE_URL=file:/app/data/custom.db \
  -v "$INSTALL/data:/app/data" -p "127.0.0.1:${APP_PORT}:3000" "$IMAGE"
```

در این مرحله مسیر عمومی، ربات و پل نباید نوشتن روی مقصد را شروع کرده باشند.
پورت و gateway داخلی مبدأ را به‌عنوان آدرس نود مقصد کپی نکنید: `tls.connectHost`
قدیمی ممکن است روی مقصد به خود سرور جدید اشاره کند، در حالی که نود روی سرور قبلی
مانده است. مسیر واقعی HTTPS، دسترسی خروجی، CA و hostname را احراز کنید. اگر API
نود فقط از شبکهٔ قبلی قابل دسترس است، ابتدا مسیر خصوصی مجاز را طراحی کنید؛ برای
حل آن پورت سرویس‌های دیگر را تغییر ندهید و TLS verification را خاموش نکنید.

در صورت نیاز فقط تنظیمات همان peer را با CLI موجود به‌روز کنید:

```bash
docker exec -i pv-reseller-dashboard node scripts/configure-node-sync.cjs PANEL_ID \
  < /root/pvnet-migration/private-peers.json
```

`PANEL_ID` همان شناسهٔ بازیابی‌شده است؛ JSON آرایهٔ **کامل** peerهای همان پنل
است، نه patch. ساختار، token، CA و masterInboundIds در
[راهنمای node sync](stale-node-client-state.md) آمده است. فایل ورودی mode 600 داشته
باشد. peer را به PanelConfig حسابداری تبدیل نکنید؛ مصرف دوبرابر می‌شود. تنظیمات
peer را برای عبور از خطا حذف نکنید؛ عملیات باید در خطای ارتباطی متوقف بماند.

## ۵. آزمون پذیرش و جابه‌جایی دامنه

1. روی DB بازیابی‌شده `PRAGMA integrity_check` باید `ok` و `PRAGMA foreign_key_check`
   بدون ردیف باشد. تعداد و محتوای جدول‌ها را با snapshot بکاپ مقایسه کنید، به‌خصوص
   `AdminUser`، `Reseller`، `ResellerUser`، `ResellerInbound`، `PanelConfig`،
   `Setting` و `OperationJournal`. سهمیه/consumedGB/رزروها و مالکیت را بازبینی کنید.
2. `curl -fsS "http://127.0.0.1:${APP_PORT}/api/auth/me"` باید پاسخ ساختاریافته بدهد؛
   این فقط health check است. ورود واقعی ادمین، 2FA در صورت فعال‌بودن و نماینده‌ها
   را از مسیر HTTPS امن آزمایش کنید. کلید معتبر باید اطلاعات اتصال و peer را
   رمزگشایی کند؛ credentialها را چاپ نکنید.
3. مصرف/انقضا/enable چند کاربر هر نماینده را با پنل مرجع و نسخهٔ نود موجود به‌صورت
   خواندنی مقایسه کنید. دادهٔ نامعلوم را صفر یا نامحدود فرض نکنید. برای آزمون
   ساخت/تمدید از DB کپی و API شبیه‌سازی‌شده استفاده کنید؛ کاربر واقعی را تغییر ندهید.
4. ژورنال‌های `PARTIAL`/`NEEDS_REPAIR`/`RUNNING` و مراحل `STARTED` را حفظ و بررسی
   کنید؛ reset با پاسخ نامعلوم را کورکورانه تکرار نکنید. حساب‌های عمداً غیرفعال،
   UUID/subId، مصرف و inboundها باید دست‌نخورده بمانند. به import کامل نود نیاز نیست.
5. فقط vhost دامنهٔ داشبورد را به loopback جدید وصل کنید. برای Apache ابتدا
   `apache2ctl configtest`، سپس reload کنترل‌شده؛ برای وب‌سرور دیگر، آزمون معادل.
   listener یا vhost سرویس دیگری را جایگزین نکنید. TLS معتبر و در Cloudflare،
   Full (strict) و bypass cache برای HTML/API این دامنه را بررسی کنید.
6. پس از پذیرش، DNS دامنهٔ داشبورد را جابه‌جا کنید؛ دامنه‌های VPN خارجی را تغییر
   ندهید. اگر دامنهٔ داشبورد عوض شود، برند/لینک‌های پل و subscription portal و
   ربات‌ها را جداگانه بازبینی کنید؛ بازیابی DB این آدرس‌ها را خودکار عوض نمی‌کند.
   مبدأ تا پایان انتشار DNS فقط بدون نوشتن نگه داشته شود. بعد فقط مقصد فعال باشد.
7. قبل/بعد، کانتینرها و زمان شروع و پورت‌های سرویس‌ها را مقایسه کنید. پورت‌های
   خروجی موقت با listener ثابت اشتباه نشوند. فقط منابع خود داشبورد می‌توانند تغییر کنند.

## ۶. بکاپ مقصد و برگشت امن

پس از سلامت مقصد و بررسی اینکه نام unitهای زیر متعلق به سرویس دیگری نیست،
تایمر را از نو برای کانتینر مقصد نصب کنید (این unitها داخل ZIP نیستند):

```bash
INSTALL_DIR="$INSTALL" CONTAINER_NAME=pv-reseller-dashboard \
  bash "$REPO/scripts/install-backup-timer.sh"
systemctl list-timers pv-reseller-backup.timer
journalctl -u pv-reseller-backup.service -n 20 --no-pager
```

زمان 03:00 Asia/Tehran و حذف ZIPهای مدیریت‌شدهٔ قدیمی‌تر از پنج روز را تأیید کنید.
از تب ادمین بکاپ تازه بگیرید، آن را در مسیر خصوصی خالی verify/restore کنید و
نسخهٔ خارج از سرور نگه دارید. فایل‌های vhost/env/network metadata لازم را نیز
جداگانه خصوصی ثبت کنید. فایل `schedule.json` به‌تنهایی اثبات فعال‌بودن تایمر نیست.

تا قبل از اولین نوشتن در مقصد، برگشت با توقف فقط داشبورد/تایمر مقصد و برگرداندن
DNS به مبدأ حفظ‌شده انجام می‌شود. بعد از نوشتن در مقصد، DB قدیمی مبدأ مرجع نیست:
ابتدا نوشتن‌ها را متوقف، بکاپ جدید بگیرید و اختلاف ژورنال/حسابداری را تعیین تکلیف
کنید؛ بازگردانی کورِ snapshot قدیمی می‌تواند سهمیه یا عملیات را دوباره اعمال کند.

## سابقهٔ بررسی

در ۲۰۲۶-۱۰-۱۷ بکاپ وضعیت سالم با ۴۸ کاربر و ۴ نماینده، تمام جدول‌ها و کلید
بازیابی با restore واقعی در پوشهٔ خصوصی موقت بررسی شد؛ سه مقدار رمزگذاری‌شده
و یک peer با کلید runtime باز شدند. سرویس‌ها و پورت‌ها تغییر نکردند. این تأیید
آرشیو است؛ انتقال به سرور مقصد جدید هنوز اجرا نشده و آزمون‌های مقصد بالا الزامی‌اند.
نام ZIP، SHA-256 و شواهد خصوصی در حافظهٔ عملیاتی نگهداری می‌شوند و در Git قرار نمی‌گیرند.
