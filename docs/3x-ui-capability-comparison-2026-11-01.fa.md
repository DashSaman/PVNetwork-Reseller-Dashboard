# مقایسهٔ امکانات پنل نمایندگی با 3x-ui

مبنای بررسی: کد همین ریپو و خواندن فقط‌خواندنیِ status و OpenAPI پنل متصل در
۱ نوامبر ۲۰۲۶؛ هر دو پاسخ HTTP 200 داشتند. OpenAPI تعداد ۱۸۸ مسیر و نسخهٔ عمومی
`3.x` را گزارش کرد؛ از این مقدار نمی‌توان شمارهٔ دقیق باینری نصب‌شده را تعیین کرد.
بررسی، شامل اجرای عملیات گروهی، تغییر کاربران یا ارتقای زیرساخت نبود.

## پیشنهادها برای پنل ما

| قابلیت | شواهد و وضعیت فعلی | پیشنهاد |
|---|---|---|
| گروه و برچسب کاربران | API متصل گروه‌ها، افزودن/حذف گروهی عضو و فیلد `group` دارد؛ مدل مالکیت ما هنوز برچسب مشتری ندارد. | اولویت بالا: گروه‌هایی مثل فروشگاه/بسته/همکار، با جستجو و فیلتر؛ هر نماینده فقط گروه‌های خودش را ببیند. |
| آخرین اتصال | API متصل `clients/lastOnline` دارد؛ پنل ما آنلاین فعلی و IP را نشان می‌دهد. | اولویت بالا: زمان آخرین اتصال و فیلتر کاربران مدت‌دارِ بدون استفاده، برای پشتیبانی. |
| مدیریت گروهی وضعیت | API متصل `bulkEnable`، `bulkDisable` و `bulkAttach` دارد؛ پنل ما ساخت گروهی و افزایش حجم/روز دارد، ولی تغییر وضعیت گروهی در رابط ندارد. | اولویت بالا: انتخاب کاربران و پیش‌نمایش تعداد، سپس فعال/غیرفعال‌سازی با کنترل مالکیت و ثبت نتیجهٔ هر کاربر. |
| زمان از اولین اتصال | قرارداد تمدید ما مدت منفی را حفظ می‌کند، اما فرم ساخت عمدتاً تاریخ یا روز از زمان ساخت می‌گیرد. | اولویت متوسط: گزینهٔ روشن «شروع اعتبار از اولین اتصال»، با نمایش همان معنا در همهٔ صفحه‌ها. |
| گزارش زمانی هر کاربر | پنل ما مصرف فعلی و نمودارهای تجمیعی دارد؛ مدل اختصاصی تاریخچهٔ روزانهٔ هر کاربر ندارد. | اولویت متوسط: نمودار مصرف روزانه و سابقهٔ تمدید/تغییر سهمیه؛ ریست شمارنده نباید مصرف منفی یا شارژ دوباره بسازد. |
| دوره‌های بازنشانی | schema متصل فیلدهای `trafficReset`، `resetDay`، `resetWeekday` و `resetMax` دارد؛ مسیر ما ریست دستی را با ثبت مصرف قطعی اجرا می‌کند. | بررسی جداگانه: دورهٔ هفتگی/ماهانه فقط پس از طراحی حسابداری؛ روشن‌کردن مستقیم ریست خودکار می‌تواند حجم رایگان بدهد. |
| هاست اختصاصی هر کاربر | schema متصل `clientHostRuleIds` دارد؛ انتشار رسمی 3.11 نیز اتصال کاربر به host rules را توضیح می‌دهد. | اولویت بعدی: الگوهای کنترل‌شدهٔ خروجی اشتراک برای بسته‌ها؛ ویرایش کامل routing و سرور به نماینده داده نشود. |
| نصب روی صفحهٔ اصلی | پروژهٔ upstream نصب به‌شکل PWA را مستند کرده است؛ در این ریپو manifest/service worker اختصاصی نداریم. | اولویت متوسط: نصب پنل نمایندگی روی موبایل؛ پاسخ‌های دارای اطلاعات کاربران و اشتراک در cache عمومی ذخیره نشوند. |

امکان هاست اختصاصی و تغییرات جدید ربات، از مستندات
[انتشار رسمی 3.11.0](https://github.com/MHSanaei/3x-ui/releases/tag/v3.11.0)
بررسی شد. نصب PWA، خروجی‌های اشتراک و امکانات کلی API در
[README رسمی](https://github.com/MHSanaei/3x-ui) و
[مستندات رسمی](https://docs.sanaei.dev/docs/) آمده است. وجود یک فیلد یا مسیر در
OpenAPI، به‌تنهایی به معنی فعال‌بودن همهٔ گزینه‌های آن روی نصب فعلی نیست.

## امکاناتی که همین حالا داریم

ساخت تکی/گروهی، افزایش گروهی حجم و روز، مولتی‌لوکیشن، سهمیه و مصرف تجمیعی،
نمودار نماینده/ادمین، بکاپ و بازیابی کنترل‌شده، برند/دامنهٔ اختصاصی، TOTP،
اعلان تلگرام و پل ربات، خروجی base64/JSON/Clash و پورتال کاربر موجودند.
بنابراین این موارد به‌عنوان قابلیتِ غایب پیشنهاد نشدند.

هشدار ۸۰٪ مصرف و ۳ روز مانده نیز در `src/lib/telegram.ts` وجود دارد و هنگام
خواندن فهرست کاربران بررسی می‌شود. پیشنهاد مفید، زمان‌بندی مستقل و قابل‌تنظیمِ
همین هشدارهاست تا وابسته به بازکردن پنل نباشند، نه ساخت دوبارهٔ اعلان موجود.

تب ادمین برای دیدن همهٔ کاربران و مسیر انتقال کاربران نمایندهٔ حذف‌شونده به مدیریت
ادمین اضافه شد. در ادامه، گروه/برچسب محلی، آخرین اتصال، وضعیت گروهی، اعتبار از
اولین اتصال، سابقهٔ مصرف نمونه‌برداری‌شده، نصب PWA و بررسی مستقل هشدارهای موجود
پیاده‌سازی شدند؛ جزئیات و آزمون‌ها در
[گزارش مدیریت کاربران](incidents/2026-11-01-scoped-customer-management.md) ثبت است.

پس از بازخورد کاربر، دکمه و نمودار جداگانهٔ «مصرف و سابقه» از ردیف کاربران
حذف شد؛ مصرف فعلی و نمودارهای تجمیعی باقی‌اند. این بخش را بدون درخواست تازه
دوباره به رابط اضافه نکنید. سابقهٔ داخلی و هشدارها حفظ شده‌اند؛ جزئیات در
[گزارش حذف نمودار هر کاربر](incidents/2026-11-01-remove-customer-history-ui.md) است.

بازنشانی دوره‌ای حجم همچنان نیازمند طراحی جداگانهٔ حسابداری است. طبق درخواست
صریح کاربر، مدیریت پروتکل‌ها، پورت‌ها، routing، هاست‌ها، نودها و هسته در پنل اصلی
و در اختیار مدیر زیرساخت باقی می‌ماند؛ مدیر نمایندگی فقط اینباندهای موجودِ مجاز
برای هر نماینده را تعیین می‌کند.
