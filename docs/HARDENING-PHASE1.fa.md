# گزارش فاز ۱ سخت‌سازی — داشبورد نمایندگی PVNetwork

تاریخ: سپتامبر ۲۰۲۶ (مهر ۱۴۰۵) — ریپو: DashSaman/PVNetwork-Reseller-Dashboard — نسخه مستقر: `5803a90`

این سند، گزارش اجرای **فاز ۱** از برنامه سخت‌سازی است (حسابداری کانونی، fail-closed، قفل اتمیک سهمیه، امنیت پایه) طبق ساختار ۲۵ بندی درخواستی. فازهای ۲ تا ۴ (ژورنال عملیات، reconciliation، دفتر کل، top-up و…) طبق فازبندی سند به دوره‌های بعد موکول شده‌اند.

## ۱. معماری موجود

لایه کنترل/حسابداری روی سرورهای خارجی 3x-ui: Next.js 16 + React 19 + TypeScript + Prisma/SQLite در کانتینر Docker (فقط لوکال 127.0.0.1:31080) پشت Apache + Let's Encrypt (+ Cloudflare اختیاری). پل 3x-ui برای ربات میرزا روی `/api/bridge/{username}`. هسته حسابداری: `Reseller.trafficPoolGB` + `ResellerUser.trafficGB` + `Reseller.consumedGB`.

## ۲. ریسک‌های production شناسایی‌شده

۱) بدهکارسازی حذف/ریست **fail-open** بود (خطای پنل بی‌صدا رد می‌شد ← بازیابی سهمیه با قطعی پنل ممکن بود). ۲) مصرف چنداینباندی در مسیر بدهکارسازی دوبار شمرده می‌شد (جمع ساده به‌جای تجمیع کانونی). ۳) `check-then-act` سهمیه بدون قفل — دو درخواست همزمان می‌توانستند پول را over-spend کنند. ۴) fallback هاردکد `APP_SECRET` در production. ۵) کوکی نشست بدون `Secure`. ۶) `ignoreBuildErrors` بیلد را از خطای TypeScript عبور می‌داد.

## ۳. فایل‌های تغییر دقیق (کامیت `5803a90`)

`src/lib/reseller-helpers.ts` (canonicalUserUsageBytes + withResellerLock + fail-closed debit) · `src/lib/user-create.ts` (قفل دور بخش بحرانی) · `src/app/api/reseller/users/route.ts` و `users/bulk/route.ts` (قفل) · `users/[email]/route.ts` (fail-closed حذف + قفل PUT/DELETE) · `users/[email]/reset-traffic/route.ts` (fail-closed + قفل) · `src/app/api/bridge/.../route.ts` (fail-closed + قفل + کوکی Secure) · `src/lib/crypto.ts` (اجبار APP_SECRET) · `src/app/api/auth/login/route.ts` (کوکی Secure) · `next.config.ts` (حذف ignoreBuildErrors) · `scripts/test-accounting.mjs` (۱۶ چک جدید).

## ۴ و ۵. مایگریشن دیتابیس و چرا امن است

فاز ۱ **هیچ مایگریشن اسکیمایی ندارد** — همه تغییرات در لایه کد است و اسکیما با BEFORE/AFTER یکسان است (تأیید مقایسه‌ای). مایگریشن‌های قبلی (ستون‌های mirza* و consumedGB) فقط-افزودنی بودند: `ADD COLUMN` با چک وجود ستون، بدون حذف/بازنویسی داده، idempotent (اجرای دوباره اسکریپت بی‌اثر است)، با بکاپ قبلی.

## ۶ و ۷. تست‌های ساخته‌شده و نتایج

`scripts/test-accounting.mjs` — ۱۶ چک روی dev server + ماک 3x-ui: race دو ساخت همزمان (فقط یکی پاس)، کسر ۳۰ گیگ با تایپ فارسی، بدهکاری کانونی ۷ گیگ برای کاربر دوباره‌نمایش‌شده در دو اینباند (نه ۱۴)، fail-closed حذف/ریست هنگام قطعی پنل (502 + رکورد دست‌نخورده)، حذف موفق با بدهکاری صحیح پس از برگشت پنل، رد ساخت ۹۹۹ گیگی از مسیر پل، بدهکاری حذف از مسیر پل (۴ گیگ). **نتیجه: ۱۶ پاس / ۰ شکست.**

## ۸. بیلد

`next build` production موفق — `✓ Compiled successfully`. خروجی standalone با کپی static/public کامل شد.

## ۹. TypeScript

`tsc --noEmit` بدون خطا در تمام مراحل؛ `ignoreBuildErrors` حذف شد — از این پس بیلد با خطای تایپ شکست می‌خورد.

## ۱۰. ESLint

`eslint` روی همه فایل‌های تغییر یافته: **۰ خطای جدید** (۴ خطای قدیمی مربوط به الگوی SortHeader در کد پیشین، خارج از دامنه این فاز).

## ۱۱. بهبودهای امنیتی

نبود `APP_SECRET` در production ← توقف استارت (fallback فقط برای dev/test)؛ پیش‌از-استقرار تأیید شد production مقدار معتبر دارد (بدون چرخش کلید). کوکی نشست داشبورد و پل: `Secure` در production + حفظ HttpOnly/SameSite. بیلد سخت‌گیرانه TypeScript. (CSRF، trusted-proxy، هدرها و SSRF ← فاز بعد، بخش ۲۳.)

## ۱۲. بهبودهای حسابداری

یک تابع کانونی `canonicalUserUsageBytes` (داخل هر پنل بیشینه، بین پنل‌ها جمع — معناشناسی شمارنده‌های 3x-ui) به‌عنوان تنها مرجع محاسبه مصرف؛ بدهکارسازی حذف/ریست از همان تابع تغذیه می‌شود؛ `consumedGB` بدون تغییر معنا باقی است.

## ۱۳. محافظت race-condition

`withResellerLock`: قفل بحرانیِ per-reseller دور «بررسی پول ← عملیات ← ثبت» در ساخت تکی/گروهی، ویرایش سهمیه (داشبورد و پل)، حذف و ریست. تست: دو درخواست همزمان ۱۰+۱۰ گیگ روی پول ۱۰ گیگی ← دقیقاً یک موفق.

## ۱۴. محافظت خرابی چندپنلی

خواندن آمار از snapshot همه پنل‌هاست؛ اگر قابل خواندن نباشد، عملیات تخریبی رد می‌شود (fail-closed). ژورنال عملیات و ردیابی replica برای PARTIAL ← فاز ۲.

## ۱۵. reconciliation

طبق فازبندی سند به فاز ۲ موکول شد (ابتدا فقط-گزارشی). زیرساخت لازم (تجمیع کانونی + fail-closed) پیش‌نیاز آن را فراهم کرده است.

## ۱۶. top-up

به فاز ۳ (دفتر کل + رزرو/کامیت/رول‌بک) موکول شد. رفتار فعلی ویرایش سهمیه با اعتبارسنجی پول (شامل مصرف قطعی) و قفل حفظ شده است.

## ۱۷. سازگاری دو نماینده فعال

مقایسه BEFORE/AFTER روی production: `ardalan` (فعال، پول ۵۱۲، تخصیص ۱، مصرف ۰، ۱ کاربر) و `Mobin` (فعال، پول ۱۰۲۴، تخصیص ۶۰، مصرف ۰، ۵ کاربر) — **دقیقاً برابر**. ۶ کاربر و ۲۱ تخصیص اینباند و ۶ subId یکتا بدون تغییر. اعتبار رمزها/2FA دست‌نخورده (فقط کد تغییر کرد).

## ۱۸. سازگاری میرزا

سطح API پل تغییری نکرد؛ تنها fail-closed و قفل اضافه شد. تست سازگاری پل روی production (لاگین فرمی + inbounds + ساخت/حذف با فرمت میرزا) در استقرار قبلی پاس شده و مسیرها در استقرار جدید زنده‌اند (پاسخ ۴۰۰ استاندارد برای ورودی نامعتبر).

## ۱۹. سازگاری سابسکریپشن

هیچ subId تغییر/چرخش نشد؛ ۶ از ۶ یکتا (بدون افزودن constraint — فقط گزارش). آدرس‌های ساب از مسیر قبلی سرو می‌شوند.

## ۲۰. بکاپ و صحت

بکاپ‌ها روی خود سرور: `/opt/pv-reseller/backup/hardening-20260928-120822` (پیش از تغییرات) و `cutover-*` (پیش از تعویض کانتینر) — با `sqlite3 .backup`، `PRAGMA integrity_check = ok`، فایل‌های .env/.installer-env/vhost/git-commit/docker-image و **SHA256SUMS تأییدشده**. هیچ سروری جایی آپلود نشده است.

## ۲۱. مراحل استقرار انجام‌شده

بکاپ صحت‌سنجی‌شده ← ثبت image/commit قبلی ← به‌روزرسانی ریپو سرور به `5803a90` ← بیلد کاندید در حال کار کانتینر قدیمی ← تعویض فقط `pv-reseller-dashboard` ← چک سلامت لوکال/مبدا/عمومی (هر سه 200) ← مقایسه invariantها ← بررسی لاگ کانتینر (بدون خطا).

ایمیج قبلی با تگ rollback موجود است: توقف/حذف کانتینر جدید و اجرای `docker run` با ایمیج rollback و همان .env/Volume (دستور استاندارد در install.sh)؛ در صورت نیاز بازگردانی `custom.db` از بکاپ تاریخ‌دار. سرورهای 3x-ui هرگز در استقرار دخیل نبوده‌اند.

## ۲۳. ریسک‌های باقی‌مانده

قفل فعلی درون-پروسه‌ای است (برای استقرار تک‌کانتینری کافی؛ چندنمونه‌ای پشتیبانی نمی‌شود). حسابداری همچنان GB اعشاری است (تبدیل به بایت/BigInt ← فاز ۳). rate-limiter درون-حافظه است. CSRF/trusted-proxy/هدرهای امنیتی/SSRF پنل ← فازهای بعد. reconciliation ندارد — ناسازگاری دستی فعلاً فقط با بررسی دستی کشف می‌شود.
