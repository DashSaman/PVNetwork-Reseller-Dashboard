## مایگریشن دیتابیس

فقط `CREATE TABLE OperationJournal` + ایندکس‌ها (افزودنی، idempotent — اجرای دوباره بی‌اثر). هیچ ستون/ردیف موجودی تغییر نمی‌کند. اسکریپت در `install.sh` (بخش migrate_database).

## رفتار جدید حذف/ریست (خلاصه)

۱. قفل نماینده ← ۲. تعیین پنل‌های مرتبط از refs ← ۳. خواندن همه پنل‌های مرتبط (اگر یکی down ← 502) ← ۴. snapshot مصرف کانونی ← ۵. ثبت ژورنال ← ۶. عملیات روی هر پنل با ثبت وضعیت ← ۷. همه موفق ← بدهکاری یک‌باره + بستن رکورد + SUCCESS؛ شکست جزئی ← PARTIAL با حفظ snapshot برای retry (retry فقط پنل‌های ناتمام و بدهکاری هرگز دوبار نیست).

## نتایج

- تست فاز ۱.۱: **۱۹ پاس / ۰ شکست** (bulk vs bulk، bulk vs single، partial reset/delete با retry، canonical داشبورد=پل=پرتال، rollback ساخت ناقص، کوکی‌ها)
- TypeScript: بدون خطا · ESLint: بدون خطای جدید · بیلد production: موفق
- استقرار روی production با بکاپ `.backup` + `integrity_check=ok` + SHA256 و مقایسه BEFORE/AFTER (مانده‌های هر دو نماینده فعال دقیقاً برابر)

## ریسک‌های باقی‌مانده

ریست PARTIAL نیازمند retry دستی (توسط خود نماینده با تلاش مجدد) است — repair خودکار خودکار ← فاز ۲. ژورنال CREATE NEEDS_REPAIR فقط ثبت می‌شود (پاکسازی دستی توسط ادمین). قفل همچنان درون-پروسه‌ای است (تک‌نمونه‌ای).
